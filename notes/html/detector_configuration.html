Detector configuration

How the detector is defined: detector cards, response-model cards and run cards with explicit overrides.

Three layersResolution rulesThe detector cardsA run cardCode, commands and tests

1. Three layers

  1. Detector set. config/detector/itaca.toml is an index naming eight cards, one per subsystem. They hold design values only. Everything that follows from them (densities, masses, the potential ladder, reduced fields, yields, drift times, spreads, counts) is computed by the resolver and shown on the detector page, never typed in a card.
  2. Response models. The VH1 and CSA amplifiers, the SiPM response model and the ASIC are device models with simulation settings, calibrations and hashes. They stay as their own cards under config/specs/response/, named by the run card and loaded by their own functions.
  3. Run card. Names the detector index, lists its [overrides] as dotted keys into the set, and carries the run parameters: events, seeds, selection, the response cards, the stages and their settings. A run is "the default detector plus what this run changes".

2. Resolution rules

  • An override key must exist in the detector set, with the same type class (number, string or boolean). A misspelt key is an error, not a new key.
  • A physical key at the top level of a run card is refused; changes go through [overrides].
  • Each stage writes resolved.toml beside its results: the detector-response stage in results/readout/<run_label>/configuration/, without the later-stage sections, so every run card that shares a detector response writes the same file; the hit-production stage in <run_label>/<output_subdir>/configuration/ with the full run. The file holds the detector values after overrides, the overrides, the run card and the SHA-256 of every input. A different content in an existing folder is an error.
  • The production scripts read the resolved detector sections directly (event_settings in run_framed_detector_response.jl) and the response cards from [response]; they accept run cards only. The cards under config/readout/ and config/specs/runs/ predate the scheme and stay as the records of their productions, with their copies saved in the HDF5 outputs.
  • Historical cards under config/readout/ and config/specs/ are not edited; their productions keep their saved copies.

# NEXT DocDB 1183, as in simulation/nexus/source/geometries/ItacaChamber.cc.

Making a run

  1. Copy a run card under config/runs/; change run_label, the event counts and the output folder.
  2. Put every changed detector value in [overrides]; nothing else in the card is physics.
  3. make vh1-production RUN=config/runs/<card>.toml runs the detector response and the VH1 hits; julia --project=. scripts/documentation/calculate_itaca_conditions.jl config/runs/<card>.toml then present_itaca_detector.py <h5> <html> make the run's own detector page with the overrides highlighted.

Check of the scheme (2026-11-15): the run card above, the default detector plus nine overrides, reproduced the detector response of the current production on 145 events and the VH1 hits of its first 100 accepted events bit for bit (scripts/validation/compare_detector_controls.jl).
