Readout implementation plan

Responsibilities, files and control plots from Monte Carlo events to itrack and etrack hits.

Agreed plan · 9 November 2026 · Implementation starts after the data types and function interfaces are reviewed.

1. Run definition and naming

For each energy deposit in a Monte Carlo event, we calculate the number of electron–ion pairs produced, including Fano fluctuations. We also assign one position to the event. The electron and ion drift distances are complementary.

A run specifies the Monte Carlo input, event numbers, detector parameters, electronics settings and reconstruction settings. The etrack and itrack use the same Monte Carlo events.

The run label includes, at minimum, the ion pitch and EL pitch. A proposed first pilot is:

bb0nu_100events_ion4mm_el4mm_XeHe15_E300_seed2026

This identifies the species, event count, both pitches, gas, drift field in V/cm and random seed. run.toml records the complete settings and selected input/output files. Further runs with different settings receive distinct labels; existing results are preserved.

events.h5 records the event numbers, assigned positions and information needed to reproduce primary electron and ion counts. Individual carrier positions are not saved.

2. Data flow

Stage 2 reads detector-response HDF5 files from Stage 1. Stage 3 reads the measured response from Stage 2 and produces reconstructed signal vectors. Hit construction reads those reconstructed vectors. Track reconstruction starts from the saved itrack and etrack hits.

Fast-trigger implementation is postponed. The acquisition region and time window are supplied as assumed trigger inputs. Their values are recorded with the run.

Each part has documented Julia functions and corresponding tests. Functions take explicitly defined data and parameters and return their results. Scripts read TOML, manage HDF5 files and execute workflows.

Reuse: existing primary-charge, transport and collection calculations in src/event_analysis; CSA forward models, statistical SiPM response and ASIC response in src/ion_signal; existing voxel and graph algorithms when track reconstruction begins.

Adapt: separate CSA voltage generation from charge reconstruction, introduce ADC-count vectors, and provide separate ion and electron reconstruction functions and files. Existing routines move as their callers are updated and their numerical behaviour is checked. Historical workflows retain their recorded settings.

Existing calibration and nonlinear CSA models must be checked at the new sampling interval and selected current waveform. A change of collection geometry or circuit requires the relevant validation.

Each itrack/etrack directory also contains settings.toml, controls.h5, index.html and a plots/ directory. Settings record the input file, parameters, calibration and code version. The run page links to every stage.

What is in a vector file?

Within each event: channel numbers and positions, vector values, time origin, sample or bucket duration, units and acquisition information. Values are integer ion counts, integer photon counts, ADC counts, or calibrated charge, according to the stage. Ion ADC counts use compressed UInt16. Reconstructed charge retains signed values and its uncertainty information.

What is in a hit file?

itracks.h5 contains event-numbered hits with x_mm, y_mm, z_mm and reconstructed ions. etracks.h5 contains the corresponding positions and reconstructed PEs. Preserve the originating channel and bucket so each hit can be traced to its signal vector. Event totals accompany the hits. The hit builder checks that their sums equal the reconstructed-vector sums.

Reusing an existing calculation

Changing ion electronics reuses detector-response files. Changing signal reconstruction reuses electronics files. Changing hit coordinates or track algorithms reuses the preceding products as appropriate.

When a file is reused, run.toml points to its existing location and records a checksum. The expected new-run output is then a reference rather than a duplicate file. The HTML page shows the actual input location. Settings and code checks determine whether reuse is valid.

Gas, coordinate convention and photon band are explicit in the files. Separate pure-Xe and Xe–He runs have distinct labels. File schemas are versioned so readers can identify the quantities they contain.

5. Intermediate control plots

Control calculations save their numerical results in controls.h5. Python generates plots and HTML from those saved results. Comparisons with Monte Carlo truth explicitly read the relevant source; reconstruction itself uses measured response and calibration.

StepControl plots and checks
Detector responseEvent totals; charge/photon accounting; mean and maximum per channel/bucket; arrival duration and number of channels; representative XY, XZ, YZ and 3D displays.
ElectronicsInput and output vectors for representative events; CSA voltage and ADC counts; SiPM charge before and after ASIC; noise distributions and correlations; affected-event and affected-sample saturation fractions.
Signal reconstructionReconstructed versus reference charge; bias and residual spread versus signal size; linear/nonlinear ion comparison; event totals and propagated uncertainties; representative reconstructed vectors.
Hit constructionVector/hit total agreement; coordinate and time conversion checks; itrack and etrack projections and 3D displays in the same coordinate system.
Track reconstruction, laterConnected components, backbone and length; endpoint charge; selection efficiencies and comparisons with the reference tracks.

Relevant numbers appear inside each plot. Histograms include entry count, mean and standard deviation, with median where useful. Residual plots include bias and RMS residual; saturation plots include the affected fraction. Standard deviation and RMS are labelled distinctly. Event displays show event number, configuration, drift distances and charge totals.

Axes include units. Captions and plot annotations identify the selection and whether entries represent events, channels or channel/bucket cells. Response mean/max comparisons use the same positive-input cells at each response stage and retain signed reconstructed values.

7. Implementation order

  1. Review interfaces: event and vector types, file contents, function signatures, units and tests. Document each in HTML before coding.
  2. Detector outputs: adapt the existing producers and readers to the agreed organisation, checking the configured drift velocities, field, bucket durations and event matching.
  3. Electronics outputs: reuse the EL response; separate the ion forward model and add voltage noise and ADC counts. Validate device response, quantisation and temporal sampling.
  4. Signal reconstruction: implement separate ion and electron functions. Establish linear ion reconstruction, then test the nonlinear inverse against independent reference signals.
  5. Hit construction: produce itrack and etrack hits and event totals, verifying charge sums and positions.
  6. Complete pilot: produce every intermediate HDF5 file and its control page. Measure time per event, file size and numerical performance before larger production.

The first milestone ends at itracks.h5 and etracks.h5. Fast-trigger implementation and track reconstruction remain subsequent work.

This page specifies proposed paths and interfaces. It does not claim that the new directories, readers or ADC implementation already exist.
